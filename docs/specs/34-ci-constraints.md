# opsalert#34 — CI tests the versions prod runs; drift is a weekly warning, never a red gate

Label: `testing` (no product code changes). Base: `lead/34-ci-constraints` (cut from integration
`e44bbc0`). Worker branch: `worker/34-ci-constraints`. One slice. Every change below is in scope;
nothing under `opsalert/` changes. Same class and same shape as debork#86.

## Why

`validate.yml` and `validate-light.yml` run `pip install -e .[dev] …` unconstrained. On 2026-10-02
that resolves SQLAlchemy 2.1.2, which installs `greenlet` only with the `[asyncio]` extra, and
`tests/conftest.py:5` (`from sqlalchemy.ext.asyncio import …`) fails at import on every branch.
Prod (vingapi `requirements.lock`) runs SQLAlchemy 2.0.46 + greenlet 3.3.1. The lead reproduced
both halves in a fresh 3.12 venv: red without greenlet; 394 passed on SQLAlchemy 2.1.2 with it.

## Rules

1. The gate tests what prod runs. Every `pip install` in a gating workflow carries
   `-c ci-constraints.txt`.
2. No upper bounds in `pyproject.toml`. SQLAlchemy stays the ONLY runtime dependency
   (`dependencies` is not touched). The library imports `sqlalchemy.ext.asyncio` only under
   `TYPE_CHECKING` or in a guarded `try`; the tests are what build async engines, so `greenlet`
   is a `dev` dependency.
3. Floating versions are checked once a week by a job that cannot gate a merge and that reports
   by issue.

## Contract

### `pyproject.toml`

- `[project.optional-dependencies].dev` gains `"greenlet>=3.0"`. Nothing else changes.

### `ci-constraints.txt` (repo root, tracked, generated)

- Header, exactly three comment lines: that the file is generated by
  `scripts/sync_ci_constraints.py` and not edited by hand; the source
  (`vingapi requirements.lock @ <vingapi commit sha>`); the command to regenerate.
- Body: every `name==version` line of the lock, in lock order, byte-identical. Excluded: every
  `-e …` line, blank lines, comments, any other option line (`--…`).
- Source for this slice: `git -C ~/vingapi show origin/main:requirements.lock` after
  `git -C ~/vingapi fetch origin main` (sha `9ae9da9d4` when the spec was written; use and record
  whatever `origin/main` is when you generate). Do NOT read `~/vingapi/requirements.lock` from the
  working tree: that checkout is detached and may be behind.

### `scripts/sync_ci_constraints.py` (stdlib only, Python 3.11+)

- `def third_party_pins(lock_text: str) -> list[str]`: the body lines as defined above.
- `def render(lock_text: str, source_sha: str) -> str`: header + body + trailing newline.
- CLI: `sync_ci_constraints.py <path-to-lock> --sha <sha> [--check]`. Without `--check` it writes
  `ci-constraints.txt` at the repo root. With `--check` it writes nothing and exits 1, printing a
  unified diff of the pins (header ignored), when the tracked file's pins differ from the lock's;
  exits 0 when they match. A missing lock path exits 2 with a message on stderr. No silent
  success.

### `.github/workflows/validate.yml` and `validate-light.yml`

- Install lines become `pip install -c ci-constraints.txt -e .[dev] ruff mypy pip-audit`
  (light: without `pip-audit`). `python -m pip install --upgrade pip` stays as it is (pip itself
  is not constrained). Nothing else in these files changes: triggers, job names, the required
  check names `validate` / `validate-light` stay byte-identical.
- `pip-audit` now audits prod's pins. If it reports a vulnerability under the constraints, STOP
  and report it to the lead with the output; do not add an ignore flag.

### `.github/workflows/validate-latest.yml` (new)

- Triggers: `schedule` cron `0 6 * * 1` (Mondays 06:00Z) and `workflow_dispatch`. No
  `pull_request`, no `merge_group`: it can never be a required check.
- Job name `latest`. `permissions: contents: read, issues: write`.
- Steps: checkout, setup-python 3.12, `pip install -e .[dev] ruff mypy` with NO constraints,
  `pip freeze` (so the log shows what resolved), ruff, mypy, pytest: same commands as
  `validate.yml`. No gitleaks, no pip-audit.
- On failure (`if: failure()`), one step using `gh` with `GH_TOKEN: ${{ github.token }}`: look for
  an OPEN issue titled exactly `validate-latest: the suite fails on unconstrained dependency
  versions`; if one exists, comment on it with the run URL; otherwise create it with label
  `testing` and a body carrying the run URL and saying the gate is unaffected (it runs under
  `ci-constraints.txt`). Exactly one open issue at any time.

### `CLAUDE.md` (repo), section `## Gates`

- Add three lines: CI installs under `ci-constraints.txt` (vingapi's lock pins); after a vingapi
  `requirements.lock` change, regenerate with `scripts/sync_ci_constraints.py`; `validate-latest`
  runs unconstrained weekly and reports by issue. Local runs that should match the gate use
  `pip install -c ci-constraints.txt -e .[dev]`.

## Acceptance tests — `tests/test_ci_constraints.py`

No DB, no async fixtures. Load the script with `importlib.util.spec_from_file_location` (it is not
part of the package). Workflows are read as text (no YAML dependency is added).

1. `test_reported_34_dev_extra_declares_greenlet` — parses `pyproject.toml` with `tomllib`; some
   entry of the `dev` extra names `greenlet`. Show it red on the base (`e44bbc0`) in the PR body.
2. `test_runtime_dependencies_are_sqlalchemy_only` — `project.dependencies` is exactly one entry
   and it names `sqlalchemy` with no extras bracket and no upper bound (`<`). Guard for rule 2.
3. `test_sync_ci_constraints_excludes_editable_lines` — a fixture lock with `name==x` lines, three
   `-e git+ssh://…` lines (the debork/opsalert/vingapi shapes from the real lock), a comment, a
   blank line and a `--hash`/`--index-url` option line: `third_party_pins` returns only the
   `==` lines, in order, unchanged.
4. `test_sync_ci_constraints_check_fails_on_drift` — in `tmp_path`: `--check` exits 0 when the
   pins match, exits 1 with the differing package named in its output when one pin differs, and
   exits 2 when the lock path does not exist. Run the CLI through `subprocess` with
   `sys.executable`; give the script a way to be pointed at a constraints path for this test
   (`--out <path>`, default the repo-root file).
5. `test_ci_constraints_has_no_editable_or_unpinned_lines` — every non-comment line of the tracked
   `ci-constraints.txt` matches `^[A-Za-z0-9_.\-]+==\S+$`, and `sqlalchemy`, `greenlet`,
   `aiosqlite`, `pytest`, `pytest-asyncio` are all present (case-insensitive, `-`/`_` folded).
6. `test_ci_constraints_match_vingapi_lock_third_party_pins` — skipped with an explicit reason
   unless env `VINGAPI_LOCK` is a path; then the tracked pins equal `third_party_pins(lock)`.
   Show it passing with `VINGAPI_LOCK` set in the PR body.
7. `test_gating_workflows_install_with_ci_constraints` — for `validate.yml` and
   `validate-light.yml`: every line containing `pip install` other than the `--upgrade pip` line
   contains `-c ci-constraints.txt`. Discover gating workflows by content, not by a hard-coded
   pair: every file under `.github/workflows/` whose text contains `pull_request` or
   `merge_group` is gating and must satisfy this. A new gating workflow is covered on arrival.
8. `test_validate_latest_never_gates_and_is_unconstrained` — `validate-latest.yml` contains
   `schedule`, contains neither `pull_request` nor `merge_group`, and no `pip install` line in it
   contains `-c ci-constraints.txt`.
